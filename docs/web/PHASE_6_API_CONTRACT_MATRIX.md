## Tenant and permission contract review

- The schema has bearer security for `/api/v1/auth/me`, customer booking operations, agency earnings, hotel PMS operations, admin payout batches, and selected admin/operations modules. This only records the OpenAPI declaration; it does not establish correct tenant filters or permission checks.
- `/api/v1/auth/me` returns the server-resolved user schema (`id`, `role`, `roles`, `admin_role`, `admin_permissions`, `agency_id`, `hotel_id`, `is_active`, `metadata`).
- The API snapshot has no portal password-login endpoint. Supabase is the token issuer; portal sign-in must use Supabase Auth and then call `/auth/me`.
- No generic agency/customer directory, agency booking operations, platform metrics, tenant directories, refund ledger, audit log, or platform subscription/entitlement endpoints are exposed in this snapshot.
- Hotel PMS operations accept hotel IDs on some paths. Their backend handlers must resolve membership and enforce property access; the frontend must use `hotel_id` returned from `/auth/me`, never a browser-selected property.
